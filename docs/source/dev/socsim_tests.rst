Testing with SOC Simulated Data
####################################################

Overview
************************************

The SOC has generated simulated L2 files for the GBTDS survey (also referred to here as "socsims").
These are located here::

    s3://stpubdata/roman/nexus/soc_simulations/r00340/l2/

The term refers to Level 2 (L2) Calibrated Science Data Files generated by the
Roman Space Telescope Science Operations Center (SOC) simulation tools for the
Wide Field Instrument (WFI), stored in the Advanced Scientific Data Format (ASDF).
These files are typically produced by simulation tools like Roman-I-Sim or
STIPS to mimic real-world data that the telescope will produce, allowing researchers
to prepare for data analysis before launch.

Key aspects of wfi_soc-simulation_l2_cal.asdf files:

* Content: They contain calibrated rate images in units of Digital Numbers per second (DN/s),
  where raw detector signals have been processed to remove instrumental effects.

* Format: ASDF is the standard file format for Roman data, storing both image arrays and metadata.

* WFI Specifics: WFI data covers a 0.281 degrees-squared field of view using 18 detectors (SCAs).

* Calibration Level (L2): L2 files are derived from Level 1 (L1) raw data (uncalibrated ramps)
  and have been processed through a simulation of the romancal pipeline to become science-ready rate images.

* Astrometry: These simulation files are designed to align with the Gaia astrometric reference frame.

* Simulation Tools: These files are generated by:

  - Roman I-Sim: A GalSim-based simulator for high-fidelity, pipeline-compatible data.

  - STIPS (Space Telescope Imaging Product Simulator): Used for creating synthetic astronomical scenes.

These files are used to test data analysis workflows, visualize the WFI field of view, and
verify astrometric and photometric precision.

The SOC sims have filenames like ``r0034001001001001001_0001_wfi01_f062_cal.asdf``.
Each file is for a given exposure and SCA.
There are 88,038 of these files available, covering 4,891 exposures and all bandpass filters.
Assuming the exposure time is 66.4 seconds, which is the predominant exposure time in the
GBTDS observation-planning files, this dataset represents approximately 3.75 days of
cumulative exposure time, which is approximately 34% of the entire GBTDS survey.


For the RAPID pipeline, fake variable sources with fixed sky positions have been added to
the ASDF files and stored here::

    s3://socsims-fakesrc-asdf-20260709/

It was discovered that the gWCS in the SOC sims is incorrect (there were no GAIA stars,
so the astrometry step failed).  We corrected this using the following Python code::

    import roman_datamodels as rdm
    from romancal.assign_wcs import AssignWcsStep
    original_dm = rdm.open(asdf_path)
    dm = AssignWcsStep.call(original_dm)

The ASDF files have been converted into FITS files and stored here::

    s3://socsims-fakesrc-fits-20260709-lite/

.. note::
    Metadata about the SOC sims are stored in a dedicated RAPID-operations PostgreSQL database.

The WCS in the FITS files is represented by the TAN-SIP projection with fifth-order SIP distortion.
Tests show this represents the WCS very well.  Two examples were examined to compare the
absolute error in the WCS between fits and the original ASDF gWCS (SCAs 2 and 9).
Across all 18 SCAs, the worst deviations are never larger than ~1e-6 of a pixel.

The above pipeline instance took about 50 minutes to execute.  Pipeline instances
that made use of already-generated reference images took about 20 minutes each to run.

The entire set of 6,917 science images took 3.7 hours to run the science pipelines that
generated the aforementioned 109 reference images and basic products (``ppid=15``),
run the post-processing pipelines (``ppid=17``), and load product metadata into the
RAPID-operations PostgresSQL database.  This translates into an overall throughput rate of
1.926 seconds per input science image.  This does not include loading SFFT-difference-image
PhotUtils catalogs into the RAPID-operations PostgresSQL database and subsequent
source cross-matching.

The PSF-fit catalogs made by the Python PhotUtils package from the SFFT difference images,
both positive and negative, were loaded into Sources child PostgreSQL database tables.
There were 259,157,881 Sources records loaded into the PostgreSQL database.
This number of sources scales up to about 10 billion sources for the entire GBTDS survey.
The elapsed time to load all sources into the database was ~3.5 hours with 8 parallel processes
(and both the VPO machine and the database-server machine have 8 vCPUs).

Cross-matching the sources with astronomical objects (called AstroObjects),
resulting in records loaded into the Merges_<field> and
AstroObjects_<fields> database tables, for all 358 fields of the sources
(i.e., fields overlapped by this test), was done.
The elapsed time to cross-match all sources was 19.2 hours with 8 parallel processes.
This includes cross-matching across field boundaries for sources near field edges.
The cross-matching was done with ``match_radius = 0.00001528`` degrees (half a Roman WFI pixel).
There were 88,747,880 AstroObjects records and 215,703,276 Merges records loaded
into the PostgreSQL database.  Of those merges (a.k.a. lightcurve data points), 33,261 merges
resulted from cross-matching across field boundaries (i.e., the match radius can extend
across a field boundary), which is an increase of 0.0154% in terms of number of merges.

The lightcurve statistics stored in the AstroObjects_<fields> database tables are updated
after the cross-matching.  This is done as a separate process from the cross-matching.
Any AstroObjects_<fields> record with no associated sources in the Merges_<field> database table are deleted.
A new Q3C index on the (meanra, meandec) columns is computed for all AstroObjects_<fields> database tables,
and then these tables are set to logged, clustered, and analyzed.
The AstroObjects_<fields> database tables are explicitly vacuumed at the end of this process.
For this test, all of these items within the process took 15.9 hours with 8 parallel processes.

This test is a small-scale, end-to-end exercise of the full VPO processing chain,
including several stages that were not part of the earlier socsims tests:
loading SExtractor difference-image catalogs into XSources database tables and cross-matching
them into XAstroObjects/XMerges, pruning not-best merges, and producing alerts with forced photometry.
The observation-date range is limited to a 10-minute window at the end of 2027-10-07,
which selects 72 science images (4 exposures x 18 SCAs, ``expid`` = 85052, 85054, 85055, 85059;
MJD 61685.99444 to 61685.99920), all for the W146 bandpass filter (``fid=8``) and overlapping 72 unique fields.

(For the objects with sources only on 2027-10-07, the missing AstroObjects records are those whose sources
are all from not-best difference images (``vbest = 0``) of earlier processing requests; these are deleted as intended.)

The cause is the version of ``computeStatisticsForAstroObjects.py`` used for the 8/21/2026 test.
It found the sources of a field only in the Sources_<obsdate>_<sca> database tables of the processing date's own jobs
(Sources_20271007_<sca>), so an astronomical object with sources only from 2027-10-01 appeared to have
no best sources.  It was deleted as "not-best" from the AstroObjects_<field> and AstroObjectsMeta_<field>
database tables, but not from the Merges_<field> database table (which is why the AstroObjects and
AstroObjectsMeta counts in the 8/21/2026 test agree).  Since 8/27/2026, the script finds the
Sources_<obsdate>_<sca> database tables of a field for all observation dates.  It builds the AstroObjectsMeta_<field>
records from the distinct ``aid`` values in Merges_<field> that join best sources, without requiring a matching
AstroObjects_<field> record, so it now writes AstroObjectsMeta records for the deleted objects.  The XAstroObjects
database tables are unaffected because they were introduced after the fix (9/30/2026).

Two weaknesses remain in the current code: the AstroObjectsMeta records are not restricted to ``aid`` values in
AstroObjects_<field>, and the "not-best" deletion removes AstroObjects records but leaves their Merges records.
The lost AstroObjects records (``aid``, ``ra0``, ``dec0``, ``flux0``) can be rebuilt from each object's first
detection in the Merges and Sources database tables; otherwise, the orphaned AstroObjectsMeta and Merges records
should be deleted.

Pruning not-best merges
----------------------------------

This test reprocessed science images that earlier processing requests had already processed, so it made 5,213
earlier difference images not best (``vbest = 0``), and with them 95,305,802 Sources records and
53,222,406 XSources records.

The VPO's ``pruneNotBestMerges.py`` (version 1.2) collected the 95,305,802 not-best sids in Python in 67.7 seconds,
and each of its 64 worker processes then sent all of them back to the database as a single
``INSERT INTO notbest_sids (sid) SELECT unnest(ARRAY[...])`` statement.  That statement is about 1.05 GB long,
which is over PostgreSQL's 1-GB limit on a single memory allocation, so all 64 workers failed with:

.. code-block::

    invalid memory alloc request size 1073741824

Because each error message repeats the query, the step's log grew to 67 GB.

In version 1.3 (pull request #309), the main process creates one shared unlogged table,
``notbest_[x]sids_<procdate>_req<N>``, loads it on the database server with ``INSERT ... SELECT`` from the
[X]Sources child tables (only the 5,213 not-best pids are sent from Python), and the workers delete from the
[X]Merges_<field> tables using it.  Run by hand, version 1.3 deleted 147,928,676 Merges records in 193.0 seconds
and 118,273,531 XMerges records in 117.2 seconds.

----------------------------------

Alerts were produced from the SFFT difference-image sources (``diff_flavor = sfft``), with
reference-catalog, NED, NED-LVS, and Gaia cross-matching, and forced photometry over a 30-day window,
for the 1,998 chips of processing request 7 (selected by ``reqid``, so only the images in the observation range).
It took three runs:

* **Run 1 was limited by the disk.**  For every previous image, forced photometry downloads the image, its PSF,
  and its uncertainty image into a staging directory, fits, and deletes them.  The staging directory is under
  ``/tmp`` in the container, which is on the instance's root EBS volume (gp3, 125 MiB/s).  For the first few minutes,
  forced photometry took about 5 seconds per previous image; once the 64 workers' staged files exceeded the
  operating system's dirty-page limit, the volume was writing a flat 125 MiB/s at 99-100% utilization for the
  rest of the run, the CPUs were about 4% busy with about 40% I/O wait, and staging and fitting averaged
  33.9 seconds per previous image.  Run 1 had done 513 chips (2.5 hours per chip) when the machine was restarted.

* **Run 2** staged to memory, with ``TMPDIR=/dev/shm`` (an in-memory file system) on the container.
  Staging and fitting took 2.1 seconds per previous image, 16 times faster, but the run stopped after 86 chips
  when the container's shell exited.

* **Run 3** staged to ``/dev/shm`` as well, with ``NUMEXPR_NUM_THREADS=1`` (checked in all of its processes).
  It completed in 24,874.9 seconds (6.91 hours), with the CPUs about 65-68% busy and no I/O wait.

Problems found in alert production:

* **Forced photometry failed for 26 chips** (1.3%), whose alerts carry no forced photometry.  Each failed on a
  DNS resolution error for the ``rapid-forced-photometry`` S3 endpoint while reading stored history, mostly at the
  start of the run, when all 64 workers read at once.  The cause is that the forced-photometry code creates a new
  S3 client, and so a new connection and DNS lookup, for every S3 request; with 16 threads in each of the
  64 workers, the lookups exceed the 1,024 packets per second that the VPC DNS resolver accepts, and the container
  does not cache DNS.  Reusing one S3 client per process would fix it.

* **701,341 previous-image files were not found (HTTP 404).**  These cost no time, but the affected
  measurements were skipped, and each was logged with a full traceback (1,402,760 traceback lines, 2.3 GB of logs):
